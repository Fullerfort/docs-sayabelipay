---
title: Getting Payment Status
description: Why polling matters — there is no push webhook to your server
---

<Warning>
  SayaBeliPay does not send your server a push notification (webhook) when a payment's status changes. There is no event subscription to configure. Status reaches you two ways, and only one of them is reliable — read on.
</Warning>

## 1. The browser redirect (not reliable on its own)

After the customer finishes (or abandons) checkout, their browser is redirected to your account's **Callback URL**, with the outcome appended as query parameters:

```
https://your-site.com/finish?transactionId=9B8FEEB60F9E3&merchantOrderNo=YOUR_ORDER_NO&status=Success
```

This is a genuinely useful signal — it's how you'd show the customer an immediate "payment successful" page — but it is **not guaranteed to happen**. If the customer closes the tab, loses connection, or their browser is blocked from redirecting for any reason, this never reaches you at all, regardless of whether the payment actually succeeded on the processor's side.

<Warning>
  Never mark an order as paid, ship a product, or grant access to a service based on this redirect alone. Treat it purely as a UX signal for the customer in front of you right now, and confirm the real status server-side before acting on it.
</Warning>

## 2. Polling the API (the reliable source of truth)

Call [`GET /api/transaction/{ref}`](/api-reference/transaction-details) with the `transactionId` you were given when you created the payment (the `transaction_id` field in the [create payment](/api-reference/create-payment) response context, i.e. your own reference — see that page for exactly which value to use).

```bash
curl https://sayabelipay.com/api/transaction/9B8FEEB60F9E3 \
  -u "YOUR_CLIENT_ID:YOUR_CLIENT_SECRET"
```

```json
{
  "status": 200,
  "data": {
    "transaction_id": "9B8FEEB60F9E3",
    "order_no": "YOUR_ORDER_NO",
    "status": "Success",
    "transaction_amount": "20.00",
    "...": "..."
  }
}
```

### Recommended pattern

1. Right after creating the payment, start polling this endpoint for that transaction on a short interval (e.g. every 5–10 seconds) — from your server, not the customer's browser.
2. Stop polling once `status` reaches a terminal value (`Success`, or a failure/error state — see below).
3. If the browser redirect arrives in the meantime, use it to update the UI immediately, but keep treating the poll result as the source of truth for actually fulfilling the order.
4. If nothing terminal happens within a reasonable window (a few minutes), stop polling on a schedule and fall back to checking manually or via [`GET /api/transactions`](/api-reference/list-transactions) later — a payment that's still genuinely pending on the processor's side can take longer than a typical polling window to resolve.

### Status values

The exact set of status strings you'll see isn't a small fixed enum — beyond `Pending` and `Success`, other values reflect whatever the underlying processor reports (e.g. `Error`, `Cancelled`, `Overdue`, `Refund`). Treat `Success` as the only value that means "money received," and treat everything else as **not yet paid** rather than trying to special-case every possible string.
